# Модель размещения быстрых ЭЗС — прототип

Статический сайт (GitHub Pages), все формулы считаются в браузере на JS,
данные лежат рядом в JSON. Спецификация: [docs/spec.txt](docs/spec.txt)
(текстовая выгрузка из docx), решения и находки — [docs/journal.md](docs/journal.md).

## Запуск

```bash
npm run generate:data        # пересоздать решётку cells.json (q — по реальным центрам); stations/centers не трогает (синтетика всех трёх — только с -- --all)
npm run assign:districts     # реальные границы округов → district в cells.json
npm run fetch:buildings      # здания OSM плитками (кэш) — только если нужно обновить данные
npm run assign:demand-layers # реальные слои спроса из OSM → cells.json (из кэша; --refresh для нового запроса POI/дорог)
npm run fit:hourly-profile   # подогнать суточный профиль p(h) под реальные DC-сессии Dundee → params.json (перед calibrate:d0)
npm run fetch:stations       # базовый data/stations.json из OSM (кэш) - добавить --refresh для нового запроса к Overpass
npm run import:yandex -- ~/Downloads/файл.har ...  # новый объезд Яндекс.Карт → компактный файл (фильтр по рубрике)
npm run merge:yandex         # довносит данные Яндекс.Карт поверх OSM-базы
npm run calibrate:d0         # пересчитать D0 и записать в data/params.json
npm run reference:equilibria # пересчитать data/reference-equilibria.json
npm test                     # Т1-Т8 подряд (полные версии, включая 50 кандидатов в Т6)
npm run check:breakeven      # разовая проверка U* для DC60-1
npm run build:mkad           # контур МКАД → data/mkad.json
npm run clip:mkad            # обрезать cells/stations по МКАД — ПОСЛЕ всех fetch/merge/assign
npm run add:planned          # плановые станции города → stations.json — после clip:mkad, ПЕРЕД calibrate:d0
npm run build:tp04           # ТП 0.4 кВ → data/tp04.json
npm run build:pool           # пул площадок → data/pool.json (кэш OSM; --refresh)
npm run compute:portfolio    # модуль 8 → data/portfolio.json (-- --n=10, -- --reuse-traditional)
```

Для просмотра сайта — любой статический сервер, например `npx serve .`
или `python3 -m http.server`. Открыть `index.html` напрямую (`file://`)
не получится — ES-модули и `fetch()` данных требуют HTTP.

Карта — OpenLayers + OSM-тайлы, полностью бесплатно, без ключей и
регистрации (сознательно не Leaflet и не Яндекс.Карты — см.
docs/journal.md, запись от 20.09).

Известные упрощения:
- **Станции и центры питания — реальные координаты, сетка спроса — ещё
  синтетика.** stations.json — 984 настоящих станции (921 внутри МКАД после обрезки): 117 из OSM (Overpass
  API) + 867 уточнённых/добавленных вручную из Яндекс.Карт через DevTools в
  два объезда (см. docs/journal.md, записи от 20.09 и 23.09). centers.json —
  227 подстанций, координаты тоже реальные (OSM, power=substation), но
  reserve_MVA/bus_planned_kW — ГРУБАЯ ОЦЕНКА по классу напряжения, а не
  измеренные данные Россетей: публичную "карту резерва мощности" МОЭСК/
  Россети МР найти не удалось, обе найденные по поиску ссылки на 23.09
  мертвы (см. journal.md). Как появятся официальные данные — заменить
  только числа резерва, координаты уже настоящие. Покрытие станций всё ещё
  неполное — независимые источники называют для Москвы ~1100+. Побочный
  эффект замены станций: пропала синтетическая механика "плановых"
  станций (реальные источники не знают о будущих), сеть теперь не растёт
  2026→2030 в модели вообще — перегрузка к 2030 выглядит более выраженной,
  чем должна быть по плану города (977 станций, раздел 3.1).
- **Районы, слои спроса и суточный профиль — реальные данные, решётка — ещё синтетика.**
  Район каждой ячейки (ЦАО/САО/...) теперь берётся из настоящих границ
  округов Москвы (OSM, `scripts/assign-real-districts.js`: admin_level=5 +
  сшивка way-сегментов в кольца + point-in-polygon), а не из секторов круга
  вокруг центра, как раньше — старая угадайка занижала площадь ЦАО в 2.6
  раза и могла присвоить кандидату ровно в центре города район "ЗелАО"
  (реальный баг, см. journal.md, 23.09). Слои привлекательности внутри
  cells.json теперь из OSM (`scripts/assign-real-demand-layers.js`): res/work
  — взвешенная плотность зданий по типу `building=*`, poi — amenity+shop,
  road — плотность/класс дорог; нормировка по 95-му перцентилю; 379 683
  здания, все 36 плиток. Известные упрощения: у 54% зданий тег
  `building=yes` (дан вес 0.3 в res — эвристика), taxi — производный
  (0.6·poi + 0.4·road), а не измеренный. Суточный профиль p(h): форма
  пиков по сегментам — из ТЗ, но поверх неё общий множитель r(h)
  (`scripts/fit-hourly-profile.js`), подогнанный так, что сумма по городу
  точно повторяет реальный профиль ~122 тыс. DC-сессий Dundee (Шотландия,
  открытые данные горсовета, 2024–2025). Почасовых данных по Москве в
  открытом доступе нет — это чужой город, заменить на сессии РСЗС при
  появлении. D0 перекалиброван: 8998.36 → 6443.86. Сетка всё ещё лежит квадратом
  1×1 км, а не по форме города.
- Станции на карте кластеризуются (`ol.source.Cluster`, js/mapview.js) —
  на текущем зуме близкие точки схлопываются в кружок с числом, клик по
  кластеру приближает карту к его границам вместо постановки кандидата.
  Расстояние группировки — в пикселях экрана, поэтому при добавлении новых
  станций в data/stations.json ничего в коде менять не нужно, кластеризация
  сама перегруппируется под новое количество.
- Перебор оборудования (модуль 6) считается только для сценария `base`.
- Быстрый черновик паспорта (клик по карте) всегда предполагает DC60-1;
  настоящий перебор всех конфигураций и выбор ω* считается отдельным,
  более медленным проходом (до 8 конфигураций × 8 локальных равновесий).
  На холодном кэше опорных равновесий — до ~50с (первый клик после
  загрузки страницы, на 984 станциях), на тёплом — единицы секунд
  (укладывается в целевые 5с из раздела 12.3 для последующих кандидатов).
  Фоновый прогрев кэша (`warmNext` в app.js) убран 22.09 — на реальных 984
  станциях он держал основной поток занятым достаточно долго, чтобы клик по
  карте не успевал зарегистрироваться в OpenLayers (см. docs/journal.md,
  запись от 22.09). Полноценный Web Worker (чтобы не блокировать основной
  поток вообще) не сделан — первый клик по-прежнему блокирует UI, но теперь
  хотя бы гарантированно регистрируется и черновик (М1-М4) рендерится сразу,
  без ожидания медленного подбора оборудования.
- Список площадок с баллами (js/scoring.js, кнопка «Добавить в список
  площадок») — быстрая надстройка по фидбеку Росатома ("список с балльной
  оценкой: доступность мощности, трафик, конкуренция в радиусе, тип района"
  + карта с тепловой подложкой), не отдельный модуль спецификации и не
  замена полного портфельного выбора (модуль 8 — блок «Где ставить новые
  станции» под картой). Мощность считается от ближайшего центра питания (координаты
  реальные, резерв мощности — оценка), район — от ближайшей ячейки
  cells.json (граница округа и слои спроса реальные, из OSM). Трафик нормализован на максимум внутри
  текущего списка, а не в абсолютных единицах — баллы сопоставимы только
  между строками одного списка. Подробности — docs/journal.md, запись от
  22.09.
- Для ΔS-чувствительных расчётов (локальный пересчёт, соседи, экономика)
  используется более точный порог сходимости, чем дефолтный из раздела 6.1.
  На реальной (кластеризованной) геометрии станций это снимает не всю
  погрешность локального пересчёта: строгий критерий Т8 (<2%) выполняется
  у 7 из 10 тестовых кандидатов на 984 станциях (плотные кластеры — до 701
  затронутых станций у одного кандидата), у остальных — до 8%, что признано
  практически приемлемым (тест требует <10%). Подробности и что проверено
  — docs/journal.md, записи от 20.09.
- U* по закрытой формуле (9.5) систематически на ~8% выше, чем даёт честный
  помесячный расчёт с тем же S* — это не баг, а разница между "годовой
  аннуитет" (CRF) и "равномерный помесячный поток". Подробности —
  docs/journal.md, запись про Т7.
- Т6 в 2026 году формально не проходит по оси времени (тау≈0.87-0.91,
  порог 0.9) — это предсказанное самой спецификацией поведение (раздел 14:
  при загрузке ~10% ось времени почти не меняет рейтинг), не баг. Т6 в
  тестах жёстко требует прохождения только для 2030. Подробности —
  docs/journal.md, запись про Т6.
- Кнопка «Проверить модель» (js/tests.js) считает Т6/Т8 в сокращённом виде
  (10 и 3 кандидата вместо 50 и 10) — иначе кнопка висела бы больше минуты.
  Полные версии — только через `npm test` в Node.
- Из оригинального задания (`~/Downloads/p_3_ru.pdf`, ООО «Росатом Сеть
  зарядных станций») — два фактора размещения, названных явно, которых в
  модели нет вообще: **электробусы** (свой режим зарядки, синхронизированный
  с расписанием маршрутов — не входят ни в один из сегментов P0/P1/T/C) и
  **накопители энергии/локальная генерация** на площадке (способ обойти
  ограничение по резерву подстанции — модуль 6 выбирает только из каталога
  обычных зарядных станций, без варианта с батарейным буфером или солнечными
  панелями). Подробности — docs/journal.md, запись от 23.09 (поздний вечер).
- В params.json три параметра без обоснования источника вообще (`source:
  "-"`): `t0_min`, `eta_ch`, `f_acq` (модули 3 и 7). Ещё один явно помечен
  недоделанным: `p_el_rub_per_kWh` — "сайт [Мосэнергосбыта] не открылся,
  первый приоритет Бори".

- **Модель считается для Москвы внутри МКАД.** Станции с Яндекс.Карт
  собирались только внутри МКАД: там 921 из 984 станций, а ячеек спроса
  снаружи было вдвое больше, чем внутри. Модель видела за МКАДом большой
  спрос без конкурентов, и рекомендации уходили туда (Коммунарка и т.п.) —
  артефакт дыры в данных. `scripts/clip-to-mkad.js` обрезает сетку спроса
  и станции по контуру МКАД; Новая Москва и приграничье — вне модели, пока
  там не собраны станции.
- **В модели только быстрые станции.** Почти половина собранных станций —
  медленные AC 22 кВт («Яндекс Заправки» почти целиком, часть «Энергии
  Москвы»); раньше они сидели в модели как быстрые 60 кВт и занижали спрос
  на станцию при калибровке D0. Теперь merge-yandex-stations.js делит на
  data/stations.json (быстрые) и data/stations-slow.json. Тип у ~30%
  станций и мощность у ~55% — оценка по оператору (помечено в полях
  kind_source/P_source).
- **Сеть растёт к 2030** (раздел 3.1): +200 плановых станций DC150-2 в год
  внутри МКАД в 2027-2030 по плану «Энергии Москвы» (500 точек/год, 80%
